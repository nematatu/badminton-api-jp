# 設計の背景

## Ramen APIから引き継ぐこと

一次資料: [フリーのWeb API、Ramen APIを作った](https://yusukebe.com/posts/2022/ramen-api/) / [Ramen API repository](https://github.com/yusukebe/ramen-api)。2022年の開発記事と、その後拡張された現行READMEを区別します。

開発記事では、学習・試作に使うAPIの選択肢、好きな題材を使う楽しさ、自身の写真資産、ページングを実装する学習機会、GitHubを通じたコンテンツ投稿が説明されています。この記事を踏まえた本プロジェクトの設計判断は次の通りです。

| 考え方 | バドミントン版への適用 |
| --- | --- |
| 好きな題材で試作する | 国内の実在会場を題材にする |
| 登録なしですぐ試す | APIキー不要・CORS対応 |
| 一覧と写真でUIを作る | 会場カード・検索・ページング、実写真と汎用図を別フィールドにする |
| Gitでデータを育てる | JSON・ローカル画像・投稿者情報をPRで管理 |
| 少ないエンドポイントで始める | 会場・投稿者を中心にREST / GraphQLを提供 |

## 対象の選択

「国内のバドミントン版」から、Ramen APIの店舗に近い単位である会場を初期対象としました。選手プロフィール・ランキング・試合速報・予約枠は対象外です。固定された小さなデータセットにより、学習時の再現性があり、外部サイト障害にAPIが依存しません。

初期データは北海道2、東京都2、神奈川県1、京都府1、福岡県1の7会場。名称・市区・設置可能面数という最小限の事実を手作業で編纂し、出典URLと確認日を付けました。未確認の面数はnull。営業時間・料金・予約可否は推測して埋めません。

## Cloudflare構成

WorkersがHonoのルーティング、静的アセット、JSONデータ、GraphQLをまとめて配信します。`run_worker_first` により共通ヘッダーを適用し、APIのタイプミスをHTMLへフォールバックさせません。DBやバインディングの手動プロビジョニングが不要です。データ更新には再デプロイが必要です。

GETはブラウザ・CDNで5分キャッシュ可能。ETagで条件付きリクエストに対応します。JSON入力の上限とGraphQLのクエリ制限を設けます。MCPは初期版には含めず、スキーマとデータ投稿の運用を先に固めます。

## 写真について

Ramen APIの魅力である実写真は、元APIの作者が持っていた写真が出発点です。今回は提供された写真がないため、公式サイト画像の転載や実在施設の生成写真で代替しません。初期版の `photos: []` は欠損を正直に表し、`illustration.kind: illustration` は汎用コート図と明示します。写真は投稿者が撮影・公開・CC BY 4.0配布の許諾を持つものだけを追加します。
